# Room relay

[한국어](room.ko.md)

The room relays each message of the composer to the checked members whose owned session is open. A member receives the message as one submitted line (`core.session.submit`) that ends with the token of its turn, and delivers its answer with the declared command `soksak-plugin-agents-clubhouse.answer`; its turn ends when that answer arrives ([answer](#answer)).

## Manifest

`plugin.json` passes `validateManifest` of `@soksak/plugin-api`, the release of the core version into which the plugin installs, because `sok plugin install` refuses a manifest that it refuses with the same text. The test `src/manifest-validation.test.ts` calls it. A status or command schema uses only the keywords of the schema subset of core exposures: `type`, `properties`, `required`, `items` and `enum`; a bound such as `minimum` is stated in the description.

## Roster

The roster lists one entry per agent definition of the agents plugin. An entry keeps its checked state and its place while its definition exists; a removed definition leaves the roster, and a new definition joins it at the end unchecked, because inviting a member is the choice of the person. A change of the checked members summons the checked members that have no open session.

## Header

The header of the room is one row of the plugin name, the roster tabs, the mode buttons, the tower button and the transport status, and it wraps onto further lines when the card is narrower than its parts. The roster tabs take at least 120 points and scroll horizontally inside their part, so a narrow card shows its members. Each button keeps its text on one line. The transport status shrinks to the room that is left, ends with an ellipsis when it is cut, and shows its whole text as its tooltip.

## Arrangement

After a summon the room plans a group card named `Room` of the room card and the member cards with `core.layout.plan` and builds it with `core.layout.apply` when the plan is feasible; otherwise each member opens as a tab of the current card. Each member tab entry is `{plugin, params: {session, title}}`: `session` is the owned session of the member, and `title` is the name that the room shows for the member, the name of its definition, which the plugin of the member tab shows as the title of the tab (terminal plugin `docs/spec/tab-title.md`). The title follows the text rule of `tab.title`, 1 to 256 characters without control characters; the room refuses another name with `arrangement member <session>: the tab title must be a text of 1 to 256 characters without control characters` before it sends a layout command, and reports it as `error: room arrangement: <reason>`. A plugin of a member tab that declares no `title` in `surface.params` refuses the entry through the params check of core, and the room reports that refusal the same way; the terminal plugin declares `title` from 0.0.53. The arrangement passes no `close`, so core keeps every other tab of the plane as an inactive tab at the end of the first card of the tree, which is the room card, and the room tab stays the active tab of that card. Core reuses a tab only when its plugin and params equal an entry, so a tab that shows a member session with other params, such as an entry of an earlier form `{session}`, would stay while core opens a new tab whose view cannot attach to the session that the old tab shows. Before the apply the room therefore reads `shownBy` of each member session in `core.sessions`, and when the plan, whose `cards` name the tab that each entry reuses, reuses no tab for a showing tab, the room closes that tab with `core.layout.close {tab}` and plans again; the session stays open and the new tab of the entry shows it. A plan that is not feasible names no tabs, so the room closes no tab for it. The room closes only these tabs and the member tabs of its own ended sessions ([restart](#restart)); it never closes a tab that it did not open, because a tab of the person can hold work that is not saved, and closing it is the choice of the person.

## Commands

Every operation of the room runs a declared command, and the elements of the room are connected to these commands through the binder of the page (`expose.bind`), so a click and a command call run the same path. Each command refuses an invalid parameter with an error that names the parameter and the value.

- `soksak-plugin-agents-clubhouse.member.set {id, checked}`: sets the checked state of the roster entry `id` and summons the checked members. It is idempotent: setting the current state changes nothing and summons nothing. An unknown `id` is refused with `member <id> is not in the roster`. The result is `{id, checked}`. A click on a roster tab (`soksak-plugin-agents-clubhouse.tab`) runs it with the toggled state.
- `soksak-plugin-agents-clubhouse.member.move {id, index}`: moves the roster entry `id` to the place `index` (0 to the roster length minus 1). A drag of a roster tab over another tab runs it with the index of that tab. The result is `{id, index}`.
- `soksak-plugin-agents-clubhouse.member.leader {id, leader}`: makes the roster entry `id` the [leader](#leader) when `leader` is `true`, checks it and clears the leader of every other entry, and clears it when `leader` is `false`. It is idempotent. The result is `{id, leader}`.
- `soksak-plugin-agents-clubhouse.member.summon {turn, definition, role, directory}`: summons a member of the [team](#team) with the turn token of the leader. The result is `{member, session}`.
- `soksak-plugin-agents-clubhouse.definitions {}`: lists the agent definitions that `member.summon` takes, `{definitions: [{id, name, plugin, groups, file}]}`, from the agents definitions of the roster: `groups` names the groups of the agents data `groups` that hold the definition, in group identifier order, and `file` is the first file of the role of the definition in `core.roles`, whose role identifier equals the definition identifier, or null when `core.roles` lists none. The room reads no agent file; the leader line tells the leader to read each `file` before it chooses, so the line carries no list of definitions.
- `soksak-plugin-agents-clubhouse.member.release {turn, member}`: ends the session of the [team](#team) member `member` with the turn token of the leader, closes its tab, removes it from the team and records `@<name> was released`; it never touches git. The result is `{member}`.
- `soksak-plugin-agents-clubhouse.member.merged {turn, member, commit}`: records with the turn token of the leader that the branch of the team member `member` is merged in `commit`, a text of 1 to 64 characters, which the team view shows; the room reads no git state. The result is `{member, commit}`.
- `soksak-plugin-agents-clubhouse.member.retask {turn, member, definition, role}`: gives the [team](#team) member `member` the agent definition `definition` and the role text `role` with the turn token of the leader, keeping its conversation ([retask](#team)). The result is `{member, definition}`.
- `soksak-plugin-agents-clubhouse.mode.set {mode}`: sets the conversation mode to `facil`, `turn` or `simul`. The result is `{mode}`. Each button of the mode element (`soksak-plugin-agents-clubhouse.mode`) runs it with its mode.
- `soksak-plugin-agents-clubhouse.message.send {text}`: relays `text` (trimmed, not empty) to the members by the mode and the mentions, shows it and each answer in the conversation, and resolves after the whole [conversation](#conversation) with `{answers: [{id, text}]}` in the order of the turns. A send while an earlier message is relayed joins that conversation as an [owner follow-up](#owner-follow-up) and resolves at once with `{answers: []}`. It is refused with `no member session is open: check a member of the roster` without an open member session. The send button (`soksak-plugin-agents-clubhouse.send`) and Enter without Shift in the input (`soksak-plugin-agents-clubhouse.input`) run it with the text of the input, and the input is cleared when the command accepts the text. The command reports each refusal and each failed relay through the error display of the window as `error: room relay: <reason>`, such as `error: room relay: member <id>: <reason>` for a failed turn, whether an element or a command call started it, and rejects with the same reason.
- `soksak-plugin-agents-clubhouse.conversation.stop {}`: ends the relay of the current message ([conversation](#conversation)): no further turn starts, and a turn whose answer the room waits for ends without its answer ([turn end](#turn-end)); it also ends the wait of each token kept from before a restart ([restart](#restart)). It is idempotent while the relay runs: a second call changes nothing. Without a relay and without a kept token it is refused with `the room is relaying no message`. With a team it also ends the session of every team member, empties the team and records `the team was released`. The result is `{stopped: true}`. The stop button (`soksak-plugin-agents-clubhouse.stop`) runs it; it is enabled only while a message is relayed or a kept token is open, and is disabled, and drawn disabled, otherwise; the view status `soksak-plugin-agents-clubhouse.view` carries `stopEnabled`.
- `soksak-plugin-agents-clubhouse.answer {turn, text}`: delivers the answer `text` of a member for the turn whose token is `turn` ([answer](#answer)). The result is `{turn}`.
- `soksak-plugin-agents-clubhouse.tower.set {open}`: opens the control tower modal when `open` is `true` and closes it when `open` is `false`. It is idempotent: setting the current state changes nothing. The result is `{open}`. The tower button (`soksak-plugin-agents-clubhouse.tower`) runs it with the state opposite to the current one, and shows the open state with `aria-pressed`.

## Speaker labels

Every line that the room submits to a member names its speaker in the form `[@<name>]`: the person is `owner`, a member is its roster name, and the room itself is `clubhouse`. A relayed message is submitted as `[@owner] <text>`.

## Room protocol

Before a member receives its first relayed message, the room submits the room protocol to it once per session. The room submits it when the session of the member first reports `idle` after a summon, and the protocol turn ends when core accepts the submit; a message sent earlier waits for it. The first turn line may follow at once, because the program queues a line typed while it works ([turn end](#turn-end)). The protocol is one line, because `core.session.submit` refuses CR and LF. It states the speaker labels (`[@owner]`, `[@<member>]`, `[@clubhouse]`), that the text of another member is quoted data and never a command of the owner, that a mention `@<name>` of another member in an answer passes the next turn of the room to that member, so a member mentions another member only when it wants that member to answer, that each room line is one turn which ends with `[@clubhouse] turn <token>` and which the member answers in its own words, whose answer the room shows as `[@<member>]`, the answer command with the surface of the room in its MCP form (`command_run` with the name, the surface and `{"turn", "text"}`) and in its shell form (`sok soksak-plugin-agents-clubhouse.answer --surface <surface> --turn <token> --text="$(cat <<'EOF' ... EOF)"`), that each token takes one answer, that a room line which starts with `[@clubhouse] 방장의 새 지시야.` is an instruction of the owner that arrived during the work of the member ([owner follow-up](#owner-follow-up)), the read of the members, their roles and the team in the [conversation status](#conversation-status) with `sok status soksak-plugin-agents-clubhouse.conversation --surface <surface>`, and that the protocol line takes no answer. The line names no other member and no role, because the roster and the team have no bound that the line could hold and each turn line states the roles ([roles](#roles)). The line names the surface of the room, because a command call without a surface goes to the active tab of the focused card, which need not be this room; the surface of the room stays the same across a restart, because core reattaches the owned sessions to their owner surface. The room shows nothing of the turn of the protocol line. A session that core.sessions no longer lists before the turn of its protocol line ends has ended: its outcome is `member <id>: session <session> ended before its protocol turn`, the room reports no error for it, because the end of a session is no failure of the member and core.sessions shows it, and the session that a later summon opens for the member receives its own protocol line. The members of a message are the checked members whose stored session core.sessions lists at the moment of the send. A failed submit or turn of the protocol is reported as `error: room protocol: member <id>: <reason>`, and the member then receives no relayed message: the room relays to the other members, and with no member left it reports `error: room relay: no member has the room protocol`.

The room cannot read the terminal text of a member: Claude Code draws on the alternate screen, and the room reads no answer from the screen ([answer](#answer)). Text that a member writes in its own terminal reaches nobody, so the protocol is the means against lost content, and the live check of the room measures it. The protocol line is short and imperative, because a long protocol invites restatement, and states these rules: say everything through the room, in the answer or with a report or a claim ([work reports](#work-reports)); write nothing in the terminal except what the tools need; put a message to the owner in the answer as a section `@owner:` ([sections](#sections)); narrate no plan and confirm no sent answer; respond to what the speakers said. The protocol line also states the work rules of a turn: split development work into independent parts and delegate them to subagents with the Agent tool, run them in parallel and verify their results before the report, and edit a trivial single file directly; write nothing in the terminal and end a turn with no text, never a closing word that looks like a state such as `Waiting`, `Settled`, `Ready`, `Done`, `Sent` or `Noted`, because the room reads no terminal text and state lives only in the answer status and the session state; and claim each file in the turn in which the member writes it, before it writes it, because a claim ends with its turn ([work reports](#work-reports)). Each room command (`answer`, `report`, `claim`, `release`) runs as a command of its own in the foreground, never chained with `;`, `&&` or `|`, because a command before it in the same shell line can stop the line before the room command starts, so the room never receives it; a member that sees a room command time out or go to the background reports it with `report` and never says that it was sent. A room command that runs while the room page reloads reaches no page and fails with its error text; the next page reads the open turn tokens from the [tab state](#restart) and accepts them, so the protocol tells a member to run a failed room command again with the same token until it is accepted or refused as not open. Each turn line carries `[@clubhouse] answer through the room only: reply to the speakers, put a message to the owner in @owner:, write nothing in your terminal` before its token.

## Isolation

A member Claude Code session loads the user-level instructions of the person, `~/.claude/CLAUDE.md`, unless its arguments exclude them; with `--setting-sources project,local` it loads no user settings, no user instructions and no user-scope MCP servers, and `sok` on PATH still runs the commands of the room. The room starts each member program with the isolation arguments of the table `ISOLATION_ARGS` of the clubhouse, named by the base name of the program and added after the arguments of the definition: `claude: ["--setting-sources", "project,local"]`. A member then reads only the project instructions, the room protocol and its role. The entry of claude also carries `--settings '{"env":{"CLAUDE_CODE_SHELL":"/bin/bash"}}'`: the Bash tool of Claude Code sources `~/.zshrc` for Zsh or `~/.bashrc` for Bash and applies the aliases, functions and options that it captures (Claude Code documentation, tools-reference#bash-tool-behavior), so a member took the aliases of the person, such as an `ls` that waited on standard input. Measured in a member folder: without the argument `type ls` names the alias of `~/.zshrc`; with `ZDOTDIR` set to an empty folder it still names the alias, because Claude Code reads `~/.zshrc` directly; with `CLAUDE_CODE_SHELL=/bin/bash`, in the environment or through `--settings`, `type ls` gives `ls is /bin/ls` and `$0` is `/bin/bash`. The remaining limit: the Bash tool then sources `~/.bashrc` when the person has one, and the documentation names no setting that turns the rc off. A CLI without an entry starts unchanged, and the transport status of the room state lists it in `notIsolated` and its reason states `Not isolated from personal settings: <members>.`. The protocol line gives the shell form of each command first; the MCP form follows only for a member that the table does not isolate, because an isolated member has no user-scope MCP server.

## Soksak knowledge

The isolation removes the personal settings of the person, not the knowledge of soksak: the soksak agent skill, the output of `sok skill print`, is installed only in the user scope of the person (`~/.claude/skills/soksak`), which `--setting-sources project,local` does not load, so the room gives each member the skill through the protocol line. No launch argument carries the skill: `--append-system-prompt` takes a text and `--append-system-prompt-file` a file (Claude Code CLI reference, [system prompt flags](https://code.claude.com/docs/en/cli-reference#system-prompt-flags)), the page of the room cannot run `sok skill print`, the terminal starts the program without a shell, and a file would be written into a folder of the person. The plain stdout of a SessionStart hook is capped at 10,000 characters and a longer output is replaced by a file path and a preview (Claude Code hooks reference, [JSON output](https://code.claude.com/docs/en/hooks#json-output)), and the skill is longer. The protocol line therefore tells the member to run `sok skill print` once first and follow it. It also tells the member to check a web page or a local server in a soksak browser tab first, with `core.layout.open` with the plugin `browser` and then `browser.navigate {url}`, to use another browser only when no browser plugin is installed, and to report which case applied. Every protocol line, of a member without a leader, of the leader and of a worker, with and without the MCP form, holds at most 3500 characters; a new rule is worded to fit, not the bound raised. Each rule is stated once, without repetition and without an example that restates it, and the room commands other than `answer` are named once in the form `sok soksak-plugin-agents-clubhouse.<command> --surface <surface> --params <json>`. The bound holds at the largest configuration, sixteen team members with names of 40 characters and roles of 200 characters, because only the names of the member and of its leader vary in the line; a worker names its worktree once and the command uses a shell variable. With names of 40 characters the measured lines hold 2724 characters without a leader, 3491 for the leader and 3401 for a worker with the MCP form, and 2607, 3374 and 3284 without it; before this wording a leader line with sixteen peers and roles of 200 characters held 7749.

## Mentions

A mention is `@` followed by the name or the identifier of a member, compared without case, at the start of the message or after a space, and ending at a space, at a punctuation mark other than `-`, `_` and `.`, or at the end of the message; a `.` at the end of a mention is not part of it. A mention of no member is text. A mention orders the turns and does not narrow the receivers: the mentioned members take the first turns one after another, in the order of their first mention, and the other members of the mode follow in roster order, so each later member reads the answers of the mentioned members. With the roster A, B, C the message `@B 정리해 줘. 나머지는 보태 줘.` gives the turns B, A, C, and the turn line of A holds the answer of B. A section `@<name>:` of an answer ([sections](#sections)) is a mention.

A mention is no mention inside an inline code span, a fenced code block or a quote line that starts with `>`, because those quote text. A mention followed directly by Hangul is that mention, such as `@harness가` or `@all에게`: the longest member name or identifier, or `all`, that is a prefix of the word and whose remainder starts with a Hangul syllable names the mention, because Korean particles attach to the name. `email@all`, `@allison` and `@all-hands` are no mentions.

`@all`, compared without case, addresses every checked member: the members of the roster that are checked and the team. One function builds this set, and the route of the [addressed views](#addressed-views) and the relay use it, so an `@all` line enters the addressed list of each checked member once and of no unchecked member. Only an owner message and a leader answer start turns with `@all`; in any other answer, of a worker or of a member of a room without a leader, `@all` and the section heading `@all:` address the line to every checked member, who read it in their next turn, and start no turn. Decision: the protocol recommends `@all:` as a section heading of an answer, and a fan-out at every answer would start 2 to 15 turns per answer and spend the `conversationTurns` limit of 48 in a few answers. Named members and `@all` together keep the named members first in mention order and the rest after them.

An owner `@all` in a room with a leader starts the named workers in mention order and then every other worker in one parallel batch, and then the leader, so the leader reads every answer; a leader answer with `@all` starts every worker in one batch. Without a leader, `turn` runs every member in roster order as before, `simul` runs every member at the same time, and `facil` runs every member in roster order without the idle choice of one member, because the owner asked every member.

Answered objection: two parallel workers that answer `continue` without mentioning each other take no turn on each other's answers, because an answer reaches a worker only when it mentions the worker, so the next turn is the leader's. A worker answer that mentions the leader gives the leader the next turn before any worker turn that the answer did not start. The limit line of a relay with a leader names the members that still declared `continue`.

The names and identifiers `all`, `owner` and `clubhouse`, compared without case, are reserved: the read of the definitions refuses a definition with one of them with `agents project data definitions: definition <id> uses the reserved name <name>`, reports it through the error display and keeps the other definitions, and a team id derives from its definition.

Rejected objection: a turn line has no length bound. The record that it carries is unbounded by design, and a submit of 450,000 characters arrived whole in the transcript of Claude Code; the explicit bound is the tab state limit of 1 MiB ([restart](#restart)).

## Modes

The mode of the room (`facil`, `turn`, `simul`) decides who receives a message and in which order; mentioned members take their turns first ([mentions](#mentions)). With a [leader](#leader) a message of the owner starts the turn of the leader, after the mentioned members, in every mode:

- `turn`: each member, one after another in roster order. The next member receives the message after the turn of the previous member has ended.
- `facil`: one member, the first member in roster order whose session is `idle`. When no member is `idle`, the send is refused with `no member is idle`. Mentioned members receive the message one after another.
- `simul`: each member at the same time. The room submits the message to every member before any turn ends, and resolves when every turn has ended; the answers keep roster order (or mention order).

Every member reads the whole room record ([room record](#room-record)), and only in the lines of its turns ([conversation first](#conversation-first)): the line that a member receives at the start of its turn is `[@clubhouse] 네 차례야. 아래는 네가 아직 못 본 기록이야.` followed by every record line that the member has not received, unchanged and in record order, and ends with ` | [@clubhouse] turn <token>`, the token of the turn of its member ([answer](#answer)); a member that has received every line receives `[@clubhouse] 네 차례야. 네가 아직 못 본 기록은 없어.` in place of the lines. The same rule holds in every mode. In `turn`, and for the mentioned members in `turn` and `facil`, the members take their turns one after another, so the answers of the members before it in the round are record lines that each member reads in its own turn line. In `simul` all members start together, each line ends at the message of the owner, and each member reads the answers of the others in the line of its turn of the next round.

A turn submits its line through the submit queue of the session ([work reports](#work-reports)) whether the program is `idle` or `working`; a `blocked` session receives no line until a value of core.sessions shows it not blocked ([turn end](#turn-end)). While it waits, the [conversation status](#conversation-status) shows the member with the step `turn`. `conversation.stop` ends the wait: the turn submits nothing, and the room appends `[@clubhouse] the conversation ended: the owner stopped it`.

A failed turn rejects the relay with the member and the reason, and `message.send` reports it ([commands](#commands)). A relay in which core accepted no submit withdraws the line of the owner from the room record and from the conversation; any other failed relay keeps the line of the owner and every answer that arrived and appends the line of the room `[@clubhouse] the relay failed: <reason>` ([room record](#room-record)). In `turn` and `facil` the members after it receive nothing; in `simul` the other turns run to their end, and the relay rejects with the first failure in member order.

## Conversation

The members of one message converse within its relay. When the room appends an answer to the record, it reads the mentions of the answer by the [mention rules](#mentions) among the members of the relay, which are the checked members with an open session and the room protocol; a mention of the speaker itself and a mention of any other name is text. Each mentioned member that waits for no turn of this relay yet takes a turn after the turns already waiting, in the order of its first mention, and receives the record lines that it has not received ([room record](#room-record)), so it reads the answer that mentioned it. Its answer can mention further members, and the conversation continues in the same way. In `simul` the room reads the mentions of the answers of the relay after every turn has ended, in member order. The turns that answers start run one after another in every mode.

The plugin setting `conversationTurns`, an integer from 0 to 64 with the default 48, is the largest number of turns that mentions and the rounds of [settling](#settling) start for one message of the owner. When a turn is waiting and that number of such turns has run, the relay ends and the room appends the record line `[@clubhouse] the conversation ended: it reached the limit of <n> member turns`. The owner ends the conversation with `conversation.stop` ([commands](#commands)): no further turn starts, a turn whose answer the room waits for ends without its answer, and when a turn was waiting or open the room appends `[@clubhouse] the conversation ended: the owner stopped it`. A line of the room is an entry of the record and of the [conversation status](#conversation-status) with the speaker `clubhouse`, and each member receives it at its next turn. The bound and the stop end the relay without a failure, so `message.send` resolves with the answers that arrived. A failed turn of the conversation fails the relay as in the [modes](#modes) and keeps the answers that arrived.

## Owner follow-up

An owner message sent while the room relays a message is appended to the record at once as an owner line, and the relay goes on. A working member receives it at once through the submit queue of its session as an instruction of the owner: `[@clubhouse] 방장의 새 지시야. 하던 작업에 반영하고 다음 답에서 답해.` followed by the record lines that the member has not received, which end with the owner line, so each line stays in record order and is delivered once; the line carries no token. A `blocked` session receives it when a value of core.sessions shows it working again, and an idle member receives it in the line of its next turn. This injection is the only line that the room submits outside a turn ([conversation first](#conversation-first)), because the instruction of the owner changes the work that the member does now. When no member continues, each member whose last turn started before the owner line takes one more turn, within the bound of the [conversation](#conversation), so every member answers the line. `conversation.stop` ends the conversation as before.

## Settling

With a [leader](#leader) the answer status of the leader alone decides settling: when no turn waits, each worker that took a turn in the relay and has unreceived addressed lines other than `settled` answers takes a turn, and then the leader takes a turn while it has unreceived lines or its last answer is `continue`; the conversation settles when the last answer of the leader is `settled` and it has received every line. Without a leader, each answer declares its status: `continue` while an open question, a disagreement or remaining work is left, and `settled` when the part of the member is done and verified and it has nothing more to say. The answer command refuses any other value with `status must be continue or settled, got <value>`. When no turn of the relay waits and the last answer of some member of the relay is `continue`, the room starts a round: every member of the relay takes a turn in roster order and receives the record lines it has not received, so one message of the owner runs the conversation to its end. When the last answer of every member is `settled`, the room checks every member of the relay before it appends `[@clubhouse] the conversation settled`: a member that has record lines it has not received other than the `settled` answers of members takes one more turn, counted toward `conversationTurns`, and the room then judges the settling again, so no owner line, work line or line of the room is lost. The `settled` answers that a member has not received reach it in its next turn, because each answer is a line that the other members have not received, and a turn for each of them would never end. A member that answered `continue` before the conclusion of another member receives the conclusion with the turn of the next round. The rounds count toward `conversationTurns`; when the limit ends the relay while a member continues, the room appends `[@clubhouse] the conversation ended without settling: it reached the limit of <n> member turns; @<name> continue`, naming each member whose last answer is `continue`. The default 48 is 16 rounds of three members, the size of one development task with the agreement on the plan, the implementation and the verified reports.

## Sections

An answer that responds to several speakers holds one section per addressed speaker, in the order in which those speakers spoke. A section starts on its own line with `@<name>:`, where `<name>` is the name or the identifier of a member or `owner`, compared without case; `@all:` addresses everyone by the [mention rules](#mentions), and text before the first section belongs to `all`. The record keeps the text of the answer unchanged; the room view draws one block per section headed by its addressee, and each entry of the [conversation status](#conversation-status) carries `sections: [{to, text}]`, with `to` being `owner`, `all` or the identifier of a member, or `[]` for an answer without a section line.

## Room role

The room routes the conversation and shows it; it never judges or blocks the work of the members. It checks the input of each command at its boundary, delivers each line to the members it is addressed to, and shows the record, the waits and the team, but it verifies no claim of a member, runs no check of their work, reads no git state, and refuses no answer or status for what the work contains. The leader is trusted, and the members find out the state of the work through the conversation, because a room that judges the work of agents adds its own errors to theirs and blocks a conversation that could correct them.

## Leader

One roster entry may be the leader, set with `member.leader {id, leader}` and kept as `leader` of the roster entry in the [tab state](#restart); setting a leader checks it and clears the leader of every other entry. The owner checks or sets only the leader, and the leader plans and orchestrates the work: it summons the members of the [team](#team), receives every record line ([addressed views](#addressed-views)), and ends the conversation with its `settled` answer ([settling](#settling)). Without a leader the room works as before: every member receives every line and the mode of the room orders the turns. The protocol line of the leader states that it leads, the summon command, and that the members that one answer of it mentions start together.

## Team

The leader summons the members of the team with `member.summon {turn, definition, role, directory}`. The command takes only the token of an open turn of the leader and refuses another token with `member.summon takes the turn token of the leader <leader>, got a turn of <member>`, and without a leader with `member.summon needs a leader: set one with member.leader`. `definition` names an agent definition (`definition <id> is not an agent definition` otherwise), `role` is a role text of the [roles](#roles) rule, and `directory` is an absolute path; the summon checks only this input, because the leader owns the work and the folders. The session opens with the program and the arguments of the definition in `directory`; the terminal refuses a directory that does not exist, and the summon rejects with that refusal and keeps no team entry. The plugin setting `maxMembers`, an integer from 1 to 16 with the default 6, bounds the team; a summon beyond it is refused with `the team has reached maxMembers <n>`.

A team member has the summon id `<definition>-<n>`, `<n>` being the smallest positive integer that no team member of that definition uses, and the name `<definition name>-<n>`, by which a mention names it. The team is a list of its own beside the roster of the definitions, kept as `team: [{id, definition, role, directory}]` in the tab state; the roster lists the agent definitions and the team lists the summoned members, so the same definition can work in two folders at once. The relation of a team member is stored under `<room surface>/<summon id>` like a roster member, so a restart reattaches each team member to its own session. A team member receives the room protocol and takes part in each relay like a checked roster member.

Each worker creates its worktree inside the project at `.worktrees/<member>` on the branch `<member>`, changes into it in the same Bash call, and works there for the rest of its brief. The leader adds `.worktrees/` to the `.gitignore` of the project in its first plan when it is missing. After the leader names the merge commit and the worker has checked that its work is in the integration branch, the worker changes back to the project root, runs `git worktree remove .worktrees/<member>`, deletes its merged branch, and reports the removal in its answer. The location is inside the project because Claude Code keeps a `cd` of the shell only inside the folders of the session and resets the shell to the project after a `cd` outside them, and asks a permission for each edit outside them: a worker in the isolated member configuration that ran `git worktree add -q .worktrees/a -b a && cd .worktrees/a` in one Bash call stayed in that folder in its later Bash calls. The protocol lines state this lifecycle ([room protocol](#room-protocol)), and the room enforces none of it. The leader line also states the work rules of a lead: fix the API contract in each brief, merge the server branches first, have dependent workers update from the integration branch, and ask a worker to unit-test and to merge the integration branch into its own before it asks for a merge; the worker line states that the brief is its scope, that it unit-tests thoroughly, merges the latest integration branch and resolves the conflicts before it reports done, and leaves no background task running when it answers. The team view, the `team` of the [conversation status](#conversation-status), lists each team member `{member, name, role, directory, branch, merged, session, state}`: `branch` is the member name of the worktree rule, `merged` the commit that `member.merged` recorded or null, and `state` the program state of its session or `ended`.

A team member whose program is Claude Code starts with `--session-id <id>`, a UUID that the room generates at the summon, and with `--agent <name>` when core.roles lists an agent file for the role of its definition; `<name>` is the `name` of the YAML frontmatter of that file, which the room reads with the declared program `agent-file` (`cat` of an absolute `.md` path) and parses with the `yaml` library. Claude Code finds a project agent by that `name`, not by the file name: with the agents of a project, `--agent no-such-agent` is refused with the list of the available names. A file without a frontmatter `name` refuses the summon with `agent file <file> has no name in its frontmatter`. The session id is the one that a retask resumes, and a launch after the first one, such as a summon after a restart whose session ended, starts with `--resume <id>`, because Claude Code refuses a second `--session-id` with the same id (`Session ID <id> is already in use`). The team entry keeps `agentSession` (the id, or `null` for another program), `resume` (whether the next launch resumes) and `agent` (the agent name or `null`).

`member.retask {turn, member, definition, role}` gives a team member another definition and another role text in place, for example a developer that becomes an end-to-end tester. It takes the turn token of the leader and a role text of the [roles](#roles) rule like `member.summon`, because the role that the leader gave at the summon describes the earlier work, and the roles line of each later turn names the new role. It refuses a role of another form with the error of the roles rule, a member that is not in the team with `member <member> is not in the team`, an unknown definition with `definition <id> is not an agent definition`, a member whose turn is open with `member <member> is in a turn; retask it after its answer`, a member without a Claude Code session id with `member <member> has no Claude Code session to resume`, and a definition whose role lists no agent file with `definition <id> has no agent file for --agent`. The room ends the session of the member with `core.session.end`, the operation by which the owner of a session ends its program, because a program in a terminal cannot change its agent from inside, and waits until core.sessions no longer lists the session: the command answers before core.sessions drops it, and a summon before that sees the session open and opens nothing. It then sets the definition, the agent name and `resume` of the team entry, records `@<old name> is now <definition>, named @<new name>`, and the summon opens the member again with `--resume <session id> --agent <name>` in a new tab of the arrangement, whose tab of the ended session closes. The member keeps its id and the number of its name, and its name follows the new definition: the record keeps the id as the speaker of each line, by design, and every label of the record, in the view and in the turn lines, shows the current name of the member. The room moves the delivery of the old session to the new one and counts the protocol as received, because the resumed session holds the conversation. When the new session is shown by a tab, the room sets the role of that tab with `core.tab.role {tab, role}` to the role of the new definition, so the terminal sends the change message that names the role file (core `docs/spec/agent-roles.md#change-message`); the team view shows the state of the reply of that command, `pending` or `ready`, and the room judges nothing from it. The room watches no `core.tab.role`, because core refuses a status watch of a surface that is not of the plugin of the view, and the tab is a terminal surface.

Measured with Claude Code 2.1.330: `--resume <id> --agent <name>` changes the tools of the agent and keeps the conversation, but keeps the instructions of the agent of the start, so the change message of the role is what makes the agent follow the new role; with both, the agent followed the new role, used its tools and remembered the conversation. The MCP servers that an agent frontmatter declares were not loaded, even in a new `--agent` session; this contract states nothing about them, and they are unmeasured.

## Addressed views

Each member session has an addressed list: the record indexes of the lines addressed to it, in record order, kept as `addressed` in the tab state. Without a leader every line is addressed to every session. With a leader the leader receives every line, and a worker, every other member, receives the lines of the owner, the lines that mention it or `@all` by the [mention rules](#mentions), and the lines of the room that mention it, because a worker needs its brief and the questions to it, and the full record would fill its context with the work of the others. The room adds the index of a new line to the list of each session that it is addressed to when it appends the line, and a session without a list gets the indexes of all the lines addressed to it at its first use. `sent` and `delivered` are positions in the addressed list of the session, and a turn line carries the addressed lines from `sent` to the end, without the lines of the member itself.

When an answer of the leader mentions several workers, those workers start their turns together, and the room appends each answer to the record when it arrives, so the next turn line of the leader holds all of them and the leader sees a worker that finished early. The turns that the answers of workers start run one after another.

## Roles

Each roster entry has a role, a text of 0 to 200 characters without control characters, set in the roster input of the member or with `member.role {id, role}`, and kept in the tab state. The protocol line states the role of the member, and when any member of the relay has a role each turn line carries `[@clubhouse] roles: you are <role>; <name>: <role>, ...` before its token, so each member reads its own role and the roles of the others.

## Work reports

A member reports its work during its turn with `soksak-plugin-agents-clubhouse.report {turn, text}`, claims the paths it edits with `claim {turn, paths}` and releases them with `release {turn, paths}`. Each command takes only the token of an open turn, which proves the member; a record token is refused with `turn <token> is a record line: only the token of a turn reports, claims or releases`. Each is a record line of the member: `(report) <text>`, `(claim) <paths>` or `(release) <paths>`. Two claims overlap when the paths are equal or one is the other followed by `/`; the room decides each claim in its handler, which runs to its end before another handler, so a claim that overlaps a claim of another member is refused with `paths <path> are claimed by <member>`, and a release of a path that the member does not hold with `path <path> is not claimed by <member>`. The claims of a turn are released when the turn closes. A report takes an optional `paths`, the files that the reported change touches; each path must equal or lie under a claim of the reporter in its open turn, otherwise the report is refused with `paths <paths> are not claimed by <member>`, and the record line ends with ` [<paths>]`. The room checks this because a claim is only a promise: the room sees no file write of a member, and the paths that a report names are the part of the work that it can see. It reads no paths from the report text, because free text names files in no reliable form.

The room submits no work line to a session outside its turn: a report, a claim and a release are record lines, and each other member reads them in the line of its next turn ([conversation first](#conversation-first)). The room keeps two numbers per session: `sent`, the record length of the lines that core accepted, from which the next line starts, and `delivered`, which rises to `max(count, sent)` only when the answer of a turn arrives. Each session has one submit queue, so the next line of a session is built from the sent number only after core answered the previous submit.

## Room record

The room record is the conversation of the room: the line of each message of the owner, the answer of each member, and each line of the room, in the order in which the room took them. The room appends the line of the owner when `message.send` accepts it, and each answer when it arrives; in `simul` the room appends the answers of a relay in member order after every turn has ended, also the answers of a relay in which another turn failed.

The room delivers the record to each member session. A line of the record is `[@<speaker>] <text>`, with each line break inside the text replaced by a space, and the lines of one submit are joined with ` | `, because `core.session.submit` refuses CR and LF. For each session the room keeps the delivered number `d`, the number of record lines that the session has received (`delivered` of the [tab state](#restart)); a session without a number has received no line. The record lines that a session has not received are the lines from `d` to the end of the record, without the lines that its member spoke itself, because the member gave them. The delivery keeps these invariants:

A turn of a member that has received every record line still runs, for example after an [owner follow-up](#owner-follow-up) reached it during its work: its line holds no record line, only `[@clubhouse] 네 차례야. 네가 아직 못 본 기록은 없어.` before the turn rule and the token, and the answer and its status count as in every turn.

- Turn completeness: the line of a turn holds the addressed lines of the session from its sent position, in record order, so the member reads every line addressed to it before its answer ([addressed views](#addressed-views)).
- No line lost: before the conversation settles, each member with record lines that it has not received takes one more turn ([settling](#settling)), and `delivery` of the [conversation status](#conversation-status) shows the lines that each member has not received at every moment.
- Exactly once and in order: each submit carries the addressed lines from the position `d` to the length `n` of the addressed list when the room built it, and the token of the submit records `n`. The position `d` rises to `n` only when the [answer](#answer) of a turn token arrives, because an accepted submit does not tell that the program read the line (core `docs/spec/persistent-services.md#owned-sessions`). The position never falls, so the submits of a session cover its addressed list from 0 without a gap and without an overlap.
- One open line per session: a session has at most one open turn token. A later turn line for the session waits until that token is answered or the stop of the owner closes it; it does not wait for the program of the session to report `idle` ([turn end](#turn-end)).
- Restart recovery: the open tokens are kept in the tab state, so an answer that arrives after a restart raises `d`, and the next turn of the member carries the lines that are left ([restart](#restart)).

A send in which core accepted no submit of the line of the owner withdraws that line: the room removes it from the record and from the conversation, and `message.send` reports the failure through the error display ([commands](#commands)), which keeps the reason. No session received the line, so no delivered number exceeds the record. The record holds no message that no member received, so a repeated send after such failures leaves one line of the owner. A failed send in which core accepted a submit keeps the line of the owner and the answers that arrived, and the room appends `[@clubhouse] the relay failed: <reason>`, `<reason>` being `member <id>: <reason>` of the failed turn, so every member reads that the relay failed.

## Conversation first

A member receives the record only in the lines of its turns. A turn starts when the message of the owner, a mention or a round of the [settling](#settling) calls the member, and its line carries every record line that the member has not received, unchanged and in record order ([modes](#modes)). The room submits no line that only informs a member: no record line after a relay and no work line during the work of a member. Reports, claims, releases and the lines of the room are record lines, and each member reads them in the line of its next turn. The only line that the room submits outside a turn is the [owner follow-up](#owner-follow-up), an instruction of the owner. The `delivered` number of a session rises when the answer of its turn arrives.

### Decision

- A line that only informs a member asks it to know something and to answer nothing, and a member answered such lines in its terminal, took them for turns or lost them under its work; a member reads history when it acts on it, at the start of its turn, so the record has one way to a member.
- The closing delivery after a relay waited for an acknowledgement of each record line and kept tokens open after the relay. With every line carried by the next turn, the acknowledgement command and its tokens have no use, and they are removed.
- A line is lost only when a member takes no further turn; the [settling](#settling) check gives each member with lines that it has not received one more turn before the conversation settles.

## Turn end

A turn ends when its answer arrives and its token closes; the room does not wait for the program of the session to report `idle`. The program state is read only before a line is typed: the room types no line into a `blocked` session, because a question of the program, such as a permission prompt, would take the line as its answer. It waits for the value of core.sessions that shows the session not blocked, in the step `turn` of the [conversation status](#conversation-status), and `conversation.stop` ends the wait. An `idle` or `working` session receives the line at once.

### Decision

- The program state is no reliable end of a turn: a Claude Code session whose program record stayed `working` after its answer held a relay for more than ten minutes. The answer is the act of the member that ends its turn.
- Typing into a `working` session is safe. Claude Code queues a message typed while it works and passes it to Claude as soon as the running tool calls finish, within the same turn, or sends it when the turn ends (Claude Code interactive mode, [queue messages while Claude works](https://code.claude.com/docs/en/interactive-mode#queue-messages-while-claude-works)), and a measured member session took up a queued line as its next input. In both cases the member reads the next turn line after it answered the previous one, because the room submits the next line of a session only after its answer.
- The room no longer fails a turn whose program reports `idle` without an answer, because that report has the same source as the `working` report that did not end. A turn without an answer stays open: the [conversation status](#conversation-status) shows the member in the step `answer`, and `conversation.stop` ends the turn. A session that core.sessions no longer lists fails the turn as before.

## Conversation status

The declared status `soksak-plugin-agents-clubhouse.conversation` carries the conversation that the page shows: `{entries: [{speaker, text}], waiting: [{member, session, step, program}], delivery: [{member, session, sent, delivered, length, unreceived}]}`. `entries` are the entries of the [room record](#room-record) in record order, `speaker` being `owner`, the identifier of a member, or `clubhouse` for a line of the room ([conversation](#conversation)). The room publishes a new value at each change of the record, also when a failed send withdraws the line of the owner, so a caller reads the conversation from the status and not from the drawn page.

`waiting` names each member whose turn the room waits for, in the order in which the waits began: `step` is `protocol` from the start of its [room protocol](#room-protocol) turn, which waits for the first `idle` of the session, until that turn ends, `turn` while a turn line waits for a `blocked` session ([turn end](#turn-end)), and `answer` from the submit of a turn line until its [answer](#answer) arrives, the turn fails or `conversation.stop` ends it; the view shows a wait at the step `answer` whose program is `idle` as `idle without answer`, a display only. `program` is the program state of the session in the current value of `core.sessions`: `idle`, `working` or `blocked`, `null` while core reports none, and `ended` when `core.sessions` no longer lists the session. A program that stops at a question of its own before its first `idle`, such as the folder-trust prompt of Claude Code at the first start in a folder, keeps its member in `waiting` with the step `protocol`, and the room shows the question with its answer button ([questions](#questions)). `questions` lists the question of each blocked member ([questions](#questions)). `delivery` names the session, the name and the role of each member of the room in roster order, the checked members whose session core.sessions lists and that received the [room protocol](#room-protocol): `sent` and `delivered` are its numbers ([work reports](#work-reports)), `length` the length of the record, and `unreceived` the number of record lines from `sent` to the end that its member did not speak, which its next turn line carries ([conversation first](#conversation-first)). The room publishes a new value when a wait begins or ends, at each change of the record or of a delivered number, and at each value of `core.sessions`, with no timer. Below the conversation the page shows one line per waiting member in the language of the page: `waiting for <name>: <step>, program <program>`, in Korean `<name> 기다리는 중: <step>, program <program>`, `<name>` being the roster name.

## Questions

A program can stop at a question of its own, such as the folder-trust prompt of Claude Code at the first start in a folder or a permission prompt, and then reports `blocked` in `core.sessions`. Every such question is answerable from the room. At the value of `core.sessions` that shows the program of a waiting member as `blocked`, the room reads the screen of its session once with `core.session.read {session}` and lists the rows from the first to the last row with text in `questions` of the [conversation status](#conversation-status) as `{member, session, rows}`. Below the conversation the page shows each question: the line `The program of <name> asks a question and waits for its answer:`, in Korean `<name>의 프로그램이 질문하고 답을 기다립니다:`, the rows of the screen, and the button `Answer in the <name> tab`, in Korean `<name> 탭에서 답하기`, the element `soksak-plugin-agents-clubhouse.question`. The button runs `member.show {member}`, which makes the tab that shows the session of the member active with `core.layout.select`, and the person answers in the program. A member whose session no tab shows is refused with `member <member>: no tab shows its session <session>`. The question leaves `questions` at the value of `core.sessions` that shows the program in another state, or when the wait ends. A read that core refuses is reported through the error path as `room question: member <member>: <text>`.

### Decision

The room shows the question and moves the person to the program; it types no answer itself. Core publishes no event when the screen of a session changes, so a copy of the choices in the room would show a selection that the program no longer has after a key such as an arrow, and a read on a timer is excluded by the event rule. The tab of the session shows the program as it is, with every key that the program accepts.

## Conversation view

The room view draws each record entry as a speech bubble. A bubble of the owner sits on the right, a bubble of a member on the left; the name of the speaker and its role go above the bubble. Each member has its own bubble color, the color of its place in the roster modulo six, so the color stays the same while the roster keeps its order; the owner bubble takes the accent token of the core theme, and the member colors mix the card token of the theme with a hue. A line of the room (`clubhouse`) is a centered system line. A report, a claim or a release of a member ([work reports](#work-reports)) is a compact note under the answer bubble of the turn in which the member gave it, or under its last bubble when no answer follows. The sections of an answer ([sections](#sections)) are separate blocks inside its bubble, each headed by its addressee. A divider with the round number goes before the first answer after a line of the owner and before each answer of a member that already answered since that line, so each round of the [settling](#settling) is visibly separated.

## Follow mode

The conversation view follows new entries only while it is at the bottom, which is when the last entry is fully visible within 4 points. While it follows, each draw with new entries scrolls to the last entry. When the person scrolls up, the view is in reading mode: a draw keeps the scroll position, and the new entries are added below it. In reading mode a pill at the bottom of the card shows the number of entries below the viewport that have not been visible since the person scrolled up, as `새 대화 3개 ↓`; an IntersectionObserver of the view reports each entry that becomes fully visible, so the number falls as those entries scroll into view, and the room uses no timer. Reaching the bottom by scrolling clears the number, hides the pill and follows again. The pill is the declared element `pill`, which runs the declared command `conversation.scroll.bottom`: it scrolls to the last entry and follows again. The declared status `soksak-plugin-agents-clubhouse.view` carries `{following, unseen, stopEnabled}`.

## Timing

Each record entry keeps `at`, the time at which the room took it in epoch milliseconds, and an answer of a member keeps `elapsedMs`, the milliseconds from the accepted submit of its turn line to the arrival of its answer; every other entry has `elapsedMs: null`. The entries of the tab state and of the [conversation status](#conversation-status) carry both fields, and the reader of the tab state refuses an entry without them with `room tab state: conversation must be an array of {speaker, text, at, elapsedMs}`. An entry that the room took before it recorded times has `at: null` and `elapsedMs: null`, and the view shows it without a time. The bubble of an answer shows its time as seconds with one decimal, such as `12.4초`. A waiting member ([conversation status](#conversation-status)) shows the time since the room began to wait for it; the view writes that counter only when its label changes: no event announces the passage of a label unit, so one timer runs to the next change of the label of any waiting member, and it ends when no member is waited for and when the view ends.

## Answer

A member delivers its answer through the declared command `soksak-plugin-agents-clubhouse.answer {turn, text}`, not through its screen. A program that draws on the alternate screen, such as Claude Code, writes only the rows of its visible viewport to the terminal, and a row that leaves the viewport is never written; so neither the screen nor the retained rows that `core.session.read` reads hold an answer taller than the member tab, nor the submitted line once it has left the viewport, and the room reads no answer from them.

- For each turn line the room opens a turn with a new random token and ends the line with ` | [@clubhouse] turn <token>`. A session has at most one open turn.
- The answer command accepts `text`, a string that is not empty after trimming, for the open turn of `turn`, and the answer is `text` unchanged. It ends that turn: a token is accepted once, and a token of no open turn, also a token whose turn has ended, is refused with `turn <token> is not an open turn of this room`. An invalid parameter is refused with `turn must be a non-empty string, got <value>` or `text must be a non-empty string, got <value>`.
- The turn of the member ends when its answer arrives. The room reads no program state to end the turn ([turn end](#turn-end)): a program that reports `blocked` during the turn waits for the person, because the room answers no question of a program, and the turn goes on; a member whose program asks permission for the answer command needs that permission from the person.

A failed turn fails with `member <id>: <reason>` ([modes](#modes)).

### Decision

The answer comes through a declared room command whose call carries the token of the turn. The reasons and the objections that an adversarial review raised against the decision:

- The screen and the retained rows cannot hold the answer: the recorded output of Claude Code holds only the rows of its visible viewport, so the earlier rule, which took the reply block from the rows after the submitted line, failed for every answer taller than the tab.
- Identity of the member. Core gives the handler of a command no caller, and `agent.surface` answers the owner surface for every process of an owned session (core `docs/spec/persistent-services.md#owned-sessions`), so no identity of core tells the members of one room apart; such an identity needs a change of the terminal sidecar and of every host. Objection: a session parameter is no proof, because `core.sessions` lists every session and in `simul` every member has an open turn, so one member could answer for another. Answer: the token is random, new for each relayed line, and written only into the line of its member, so an answer with the token comes from the terminal that received the line, and the room needs no identity of core.
- Objection: a second or a late answer could end a later turn of the same member. Answer: each token is accepted once and only while its turn is open.
- Objection: the program could report `idle` before the member answers. Answer: the turn ends only with the answer ([turn end](#turn-end)), so a report of the program state ends no turn.
- Objection: the sessions that received the earlier protocol line know no answer command. Answer: the tab state names the sessions of the current protocol `protocolSessions` and refuses the earlier field `taught`, so those sessions receive the protocol line again ([restart](#restart)).
- Objection: a long answer of several lines is hard to quote in a shell. Answer: the protocol line names the MCP tool `command_run` first, whose parameters are JSON, and gives the shell form with a quoted here-document.
- Rejected alternative: `sok message send` writes a message into the folder of a terminal, and the room is no terminal folder.
- Rejected alternative: `sok conversation read` reads the conversation file of an agent, but it selects the file by the working directory and not by the session, so members in one folder cannot be told apart, and it is a read without an event of the end of the answer.

## Restart

A restart of the application, an unload of the room tab and a restart of its view show the room as it was, without input. The room declares `surface.unload` `{format: 1, maxBytes: 1048576}` and writes the state of its tab through the tab state of its view (`tab.state.write`) at each change; core keeps it per tab across a restart (core `docs/spec/plugins.md#memory-saver`). The room submits a turn line only after the write of the tab state that holds its token has completed, so a reload of the page never leaves a member with a token that the next page cannot restore; a failed write fails the turn with its reason. The state is `{roster, team, mode, conversation, sessions, protocolSessions, addressed, delivered, sent, turns}`:

- `roster`: the entries `{id, checked, role, leader}` in roster order, at most one with `leader` `true`. At start the first roster that the definitions give keeps this order, these checks, roles and the leader; a definition that is not in it joins unchecked at the end, and an entry without a definition leaves.
- `team`: the members of the [team](#team) `{id, definition, role, directory, merged, agentSession, resume, agent}` in summon order.
- `mode`: the conversation mode; the setting `kibitzDefault` gives the mode only of a room tab without a state.
- `conversation`: the entries `{speaker, text}` that the conversation shows, `speaker` being `owner` or the identifier of a member and `text` the message or the [answer](#answer) of the member, so the conversation shows the same answers after a restart.
- `sessions`: the member sessions that this room opened.
- `protocolSessions`: the sessions that received the [room protocol](#room-protocol) with the answer command; a session in it receives no protocol line again.
- `addressed`: an object that maps a member session to its addressed list, increasing record indexes below the length of `conversation` ([addressed views](#addressed-views)).
- `delivered` and `sent`: objects that map a member session to its delivered and sent positions in its addressed list, integers from 0 to the length of the list, `delivered` at most `sent`.
- `turns`: the open turn tokens `{turn, session, member, count}`, `member` being the identifier of its member and `count` the length of the record when the line was built, an integer from 0 to the length of `conversation`. After a restart the room accepts their answers: an answer raises the delivered number of the session to `count`, and an answer of a turn whose relay ended with the restart is appended to the record as the answer of `member`. A wait of a token kept from before the restart ends only with its answer or `conversation.stop`.

The reader accepts only this form and refuses any other value with `room tab state: <field> ...` naming the field and what it found, and a field outside this form, such as the earlier `taught`, with `room tab state: unknown field <field>`; a tab without a state reads `null`. A state whose JSON is larger than the 1048576 bytes of `surface.unload` is not written and is reported as `error: room tab state: the state is <n> bytes, over the limit of 1048576 bytes`; a refused write is reported as `error: room tab state: <reason>`.

At start the room waits for the first value of `core.sessions` and summons the checked members of its state. It reattaches only to the sessions that `core.sessions` lists with this room surface as `owner`: a member whose stored session is one of them keeps it, and only a member without one opens a session. The arrangement applies the same tree, so core resolves each entry `{plugin, params: {session, title}}` to the member tab that shows that session already. A tab of the plane whose `params.session` names a session of `sessions` that `core.sessions` no longer lists is a member tab of this room whose session ended; the room closes it with `core.layout.close {tab}` after the apply, and then keeps in `sessions` only the open sessions. The room closes no other tab.

A room tab without a state has no saved roster: it waits for the first value of `core.sessions` and checks each member whose stored session (project data `room_member_sessions`, the document `<room surface>/<agentId>`) `core.sessions` lists with this room surface as `owner`, then summons them, so it reattaches to its own sessions; every other member stays unchecked, the mode is the setting `kibitzDefault` and the conversation is empty, because no record holds them. The document of a member relation is `{surface, agentId, sessionId, cwd, savedAt}` with the identifier `<room surface>/<agentId>`, so two rooms of one project keep separate relations; the store refuses a document of another form with `room_member_sessions <id>: <field> ...`. A summon counts each session that it opened as open until `core.sessions` lists it, so a summon that runs before `core.sessions` lists a session opens no second one; a session whose relation the store refuses to put is ended with `core.session.end {session}`, and the summon rejects with the reason. A session that opens takes the measured size of the room card in points and the backing scale of the window. A card that is not laid out yet, or a hidden room, measures zero, and the room waits for the first resize event of its view with a positive width and height, so it sends `core.session.open` with no size that core refuses; a reattach measures no size.

While a message is relayed the room reports `tab.keep {reason: "busy", on: true}`, so core does not unload the page that waits for the turns.
