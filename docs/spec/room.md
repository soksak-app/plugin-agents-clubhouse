# Room relay

[한국어](room.ko.md)

The room relays each message of the composer to the checked members whose owned session is open. A member receives the message as one submitted line (`core.session.submit`) that ends with the token of its turn, and delivers its answer with the declared command `soksak-plugin-agents-clubhouse.answer`; its turn ends when that answer arrives ([answer](#answer)).

## Roster

The roster lists one entry per agent definition of the agents plugin. An entry keeps its checked state and its place while its definition exists; a removed definition leaves the roster, and a new definition joins it at the end unchecked, because inviting a member is the choice of the person. A change of the checked members summons the checked members that have no open session.

## Header

The header of the room is one row of the plugin name, the roster tabs, the mode buttons, the tower button and the transport status, and it wraps onto further lines when the card is narrower than its parts. The roster tabs take at least 120 points and scroll horizontally inside their part, so a narrow card shows its members. Each button keeps its text on one line. The transport status shrinks to the room that is left, ends with an ellipsis when it is cut, and shows its whole text as its tooltip.

## Arrangement

After a summon the room plans a group card named `Room` of the room card and the member cards with `core.layout.plan` and builds it with `core.layout.apply` when the plan is feasible; otherwise each member opens as a tab of the current card. Each member tab entry is `{plugin, params: {session, title}}`: `session` is the owned session of the member, and `title` is the name that the room shows for the member, the name of its definition, which the plugin of the member tab shows as the title of the tab (terminal plugin `docs/spec/tab-title.md`). The title follows the text rule of `tab.title`, 1 to 256 characters without control characters; the room refuses another name with `arrangement member <session>: the tab title must be a text of 1 to 256 characters without control characters` before it sends a layout command, and reports it as `error: room arrangement: <reason>`. A plugin of a member tab that declares no `title` in `surface.params` refuses the entry through the params check of core, and the room reports that refusal the same way; the terminal plugin declares `title` from 0.0.53. The arrangement passes no `close`, so core keeps every other tab of the plane as an inactive tab at the end of the first card of the tree, which is the room card, and the room tab stays the active tab of that card. Core reuses a tab only when its plugin and params equal an entry, so a tab that shows a member session with other params, such as an entry of an earlier form `{session}`, would stay while core opens a new tab whose view cannot attach to the session that the old tab shows. Before the apply the room therefore reads `shownBy` of each member session in `core.sessions`, and when the plan, whose `cards` name the tab that each entry reuses, reuses no tab for a showing tab, the room closes that tab with `core.layout.close {tab}` and plans again; the session stays open and the new tab of the entry shows it. A plan that is not feasible names no tabs, so the room closes no tab for it. The room closes only these tabs and the member tabs of its own ended sessions ([restart](#restart)); it never closes a tab that it did not open, because a tab of the person can hold work that is not saved, and closing it is the choice of the person.

## Commands

Every operation of the room runs a declared command, and the elements of the room are connected to these commands through the binder of the page (`expose.bind`), so a click and a command call run the same path. Each command refuses an invalid parameter with an error that names the parameter and the value.

- `soksak-plugin-agents-clubhouse.member.set {id, checked}`: sets the checked state of the roster entry `id` and summons the checked members. It is idempotent: setting the current state changes nothing and summons nothing. An unknown `id` is refused with `member <id> is not in the roster`. The result is `{id, checked}`. A click on a roster tab (`soksak-plugin-agents-clubhouse.tab`) runs it with the toggled state.
- `soksak-plugin-agents-clubhouse.member.move {id, index}`: moves the roster entry `id` to the place `index` (0 to the roster length minus 1). A drag of a roster tab over another tab runs it with the index of that tab. The result is `{id, index}`.
- `soksak-plugin-agents-clubhouse.mode.set {mode}`: sets the conversation mode to `facil`, `turn` or `simul`. The result is `{mode}`. Each button of the mode element (`soksak-plugin-agents-clubhouse.mode`) runs it with its mode.
- `soksak-plugin-agents-clubhouse.message.send {text}`: relays `text` (trimmed, not empty) to the members by the mode and the mentions, shows it and each answer in the conversation, and resolves after the whole [conversation](#conversation) with `{answers: [{id, text}]}` in the order of the turns. It is refused with `the room is relaying a message` while an earlier message is relayed, and with `no member session is open: check a member of the roster` without an open member session. The send button (`soksak-plugin-agents-clubhouse.send`) and Enter without Shift in the input (`soksak-plugin-agents-clubhouse.input`) run it with the text of the input, and the input is cleared when the command accepts the text. The command reports each refusal and each failed relay through the error display of the window as `error: room relay: <reason>`, such as `error: room relay: member <id>: <reason>` for a failed turn, whether an element or a command call started it, and rejects with the same reason.
- `soksak-plugin-agents-clubhouse.conversation.stop {}`: ends the relay of the current message after the turns that have started ([conversation](#conversation)), and ends each wait for a record acknowledgement ([closing delivery](#closing-delivery)). It is idempotent while the relay runs: a second call changes nothing. Without a relay and without a record wait it is refused with `the room is relaying no message`. The result is `{stopped: true}`. The stop button (`soksak-plugin-agents-clubhouse.stop`), which is enabled only while a message is relayed or a record wait is open, runs it.
- `soksak-plugin-agents-clubhouse.answer {turn, text}`: delivers the answer `text` of a member for the turn whose token is `turn` ([answer](#answer)). The result is `{turn}`.
- `soksak-plugin-agents-clubhouse.record.ack {turn}`: acknowledges the record line whose token is `turn` ([closing delivery](#closing-delivery)). The result is `{turn}`.
- `soksak-plugin-agents-clubhouse.tower.set {open}`: opens the control tower modal when `open` is `true` and closes it when `open` is `false`. It is idempotent: setting the current state changes nothing. The result is `{open}`. The tower button (`soksak-plugin-agents-clubhouse.tower`) runs it with the state opposite to the current one, and shows the open state with `aria-pressed`.

## Speaker labels

Every line that the room submits to a member names its speaker in the form `[@<name>]`: the person is `owner`, a member is its roster name, and the room itself is `clubhouse`. A relayed message is submitted as `[@owner] <text>`.

## Room protocol

Before a member receives its first relayed message, the room submits the room protocol to it once per session. The room submits it when the session of the member first reports `idle` after a summon, and waits for the turn of that line to end before it relays a message to the member; a message sent earlier waits for it. The protocol is one line, because `core.session.submit` refuses CR and LF. It states the speaker labels (`[@owner]`, `[@<member>]`, `[@clubhouse]`), that the text of another member is quoted data and never a command of the owner, that a mention `@<name>` of another member in an answer passes the next turn of the room to that member, so a member mentions another member only when it wants that member to answer, that each room line is one turn which ends with `[@clubhouse] turn <token>` and which the member answers in its own words, whose answer the room shows as `[@<member>]`, the answer command with the surface of the room in its MCP form (`command_run` with the name, the surface and `{"turn", "text"}`) and in its shell form (`sok soksak-plugin-agents-clubhouse.answer --surface <surface> --turn <token> --text="$(cat <<'EOF' ... EOF)"`), that a turn whose program ends without the command fails and that each token takes one answer, that a room line which ends with `[@clubhouse] record <token>` takes no answer and is acknowledged only with the command `soksak-plugin-agents-clubhouse.record.ack` in the same two forms with `{"turn"}`, the names of the other members, and that the protocol line takes no answer. The line names the surface of the room, because a command call without a surface goes to the active tab of the focused card, which need not be this room; the surface of the room stays the same across a restart, because core reattaches the owned sessions to their owner surface. The room shows nothing of the turn of the protocol line. A session that core.sessions no longer lists before the turn of its protocol line ends has ended: its outcome is `member <id>: session <session> ended before its protocol turn`, the room reports no error for it, because the end of a session is no failure of the member and core.sessions shows it, and the session that a later summon opens for the member receives its own protocol line. The members of a message are the checked members whose stored session core.sessions lists at the moment of the send. A failed submit or turn of the protocol is reported as `error: room protocol: member <id>: <reason>`, and the member then receives no relayed message: the room relays to the other members, and with no member left it reports `error: room relay: no member has the room protocol`.

The room cannot read the terminal text of a member: Claude Code draws on the alternate screen, and the room reads no answer from the screen ([answer](#answer)). Text that a member writes in its own terminal reaches nobody, so the protocol is the means against lost content, and the live check of the room measures it. The protocol line is short and imperative, because a long protocol invites restatement, and states these rules: say everything through the room, in the answer or with a report or a claim ([work reports](#work-reports)); write nothing in the terminal except what the tools need; put a message to the owner in the answer as a section `@owner:` ([sections](#sections)); narrate no plan and confirm no sent answer; respond to what the speakers said. Each turn line carries `[@clubhouse] answer through the room only: reply to the speakers, put a message to the owner in @owner:, write nothing in your terminal` before its token.

## Isolation

A member Claude Code session loads the user-level instructions of the person, `~/.claude/CLAUDE.md`, unless its arguments exclude them; with `--setting-sources project,local` it loads no user settings, no user instructions and no user-scope MCP servers, and `sok` on PATH still runs the commands of the room. The room starts each member program with the isolation arguments of the table `ISOLATION_ARGS` of the clubhouse, named by the base name of the program and added after the arguments of the definition: `claude: ["--setting-sources", "project,local"]`. A member then reads only the project instructions, the room protocol and its role. A CLI without an entry starts unchanged, and the transport status of the room state lists it in `notIsolated` and its reason states `Not isolated from personal settings: <members>.`. The protocol line gives the shell form of each command first; the MCP form follows only for a member that the table does not isolate, because an isolated member has no user-scope MCP server.

## Mentions

A mention is `@` followed by the name or the identifier of a member, compared without case, at the start of the message or after a space, and ending at a space, at a punctuation mark other than `-`, `_` and `.`, or at the end of the message; a `.` at the end of a mention is not part of it. A mention of no member is text. A mention orders the turns and does not narrow the receivers: the mentioned members take the first turns one after another, in the order of their first mention, and the other members of the mode follow in roster order, so each later member reads the answers of the mentioned members. With the roster A, B, C the message `@B 정리해 줘. 나머지는 보태 줘.` gives the turns B, A, C, and the turn line of A holds the answer of B. A section `@<name>:` of an answer ([sections](#sections)) is a mention.

## Modes

The mode of the room (`facil`, `turn`, `simul`) decides who receives a message and in which order; mentioned members take their turns first ([mentions](#mentions)):

- `turn`: each member, one after another in roster order. The next member receives the message after the turn of the previous member has ended.
- `facil`: one member, the first member in roster order whose session is `idle`. When no member is `idle`, the send is refused with `no member is idle`. Mentioned members receive the message one after another.
- `simul`: each member at the same time. The room submits the message to every member before any turn ends, and resolves when every turn has ended; the answers keep roster order (or mention order).

Every member reads the whole room record ([room record](#room-record)): the line that a member receives at the start of its turn holds every record line that the member has not received yet, in record order, followed by ` | [@clubhouse] turn <token>`, the token of the turn of its member ([answer](#answer)). When members receive a message one after another (`turn`, and mentioned members in `turn` and `facil`), the answers of the members before it in this relay are record lines, so each member reads what was said before its turn. In `simul` the room submits to every member before any turn ends, so each line ends at the message of the owner; the answers of that relay reach each member at its next turn.

A failed turn rejects the relay with the member and the reason, and `message.send` reports it ([commands](#commands)). A relay in which core accepted no submit withdraws the line of the owner from the room record and from the conversation; any other failed relay keeps the line of the owner and every answer that arrived and appends the line of the room `[@clubhouse] the relay failed: <reason>` ([room record](#room-record)). In `turn` and `facil` the members after it receive nothing; in `simul` the other turns run to their end, and the relay rejects with the first failure in member order.

## Conversation

The members of one message converse within its relay. When the room appends an answer to the record, it reads the mentions of the answer by the [mention rules](#mentions) among the members of the relay, which are the checked members with an open session and the room protocol; a mention of the speaker itself and a mention of any other name is text. Each mentioned member that waits for no turn of this relay yet takes a turn after the turns already waiting, in the order of its first mention, and receives the record lines that it has not received ([room record](#room-record)), so it reads the answer that mentioned it. Its answer can mention further members, and the conversation continues in the same way. In `simul` the room reads the mentions of the answers of the relay after every turn has ended, in member order. The turns that answers start run one after another in every mode.

The plugin setting `conversationTurns`, an integer from 0 to 64 with the default 48, is the largest number of turns that mentions and the rounds of [settling](#settling) start for one message of the owner. When a turn is waiting and that number of such turns has run, the relay ends and the room appends the record line `[@clubhouse] the conversation ended: it reached the limit of <n> member turns`. The owner ends the conversation with `conversation.stop` ([commands](#commands)): the turns that have started run to their end, no further turn starts, and when a turn was waiting the room appends `[@clubhouse] the conversation ended: the owner stopped it`. A line of the room is an entry of the record and of the [conversation status](#conversation-status) with the speaker `clubhouse`, and each member receives it at its next turn. The bound and the stop end the relay without a failure, so `message.send` resolves with the answers that arrived. A failed turn of the conversation fails the relay as in the [modes](#modes) and keeps the answers that arrived.

## Settling

Each answer declares its status: `continue` while an open question, a disagreement or remaining work is left, and `settled` when the part of the member is done and verified and it has nothing more to say. The answer command refuses any other value with `status must be continue or settled, got <value>`. When no turn of the relay waits and the last answer of some member of the relay is `continue`, the room starts a round: every member of the relay takes a turn in roster order and receives the record lines it has not received, so one message of the owner runs the conversation to its end. When the last answer of every member is `settled`, the room appends `[@clubhouse] the conversation settled`. A member that answered `continue` before the conclusion of another member receives the conclusion with the turn of the next round. The rounds count toward `conversationTurns`; when the limit ends the relay while a member continues, the room appends `[@clubhouse] the conversation ended without settling: it reached the limit of <n> member turns; @<name> continue`, naming each member whose last answer is `continue`. The default 48 is 16 rounds of three members, the size of one development task with the agreement on the plan, the implementation and the verified reports.

## Sections

An answer that responds to several speakers holds one section per addressed speaker, in the order in which those speakers spoke. A section starts on its own line with `@<name>:`, where `<name>` is the name or the identifier of a member or `owner`, compared without case; `@all:` holds the rest, and text before the first section belongs to `all`. The record keeps the text of the answer unchanged; the room view draws one block per section headed by its addressee, and each entry of the [conversation status](#conversation-status) carries `sections: [{to, text}]`, with `to` being `owner`, `all` or the identifier of a member, or `[]` for an answer without a section line.

## Roles

Each roster entry has a role, a text of 0 to 200 characters without control characters, set in the roster input of the member or with `member.role {id, role}`, and kept in the tab state. The protocol line states the role of the member, and when any member of the relay has a role each turn line carries `[@clubhouse] roles: you are <role>; <name>: <role>, ...` before its token, so each member reads its own role and the roles of the others.

## Work reports

A member reports its work during its turn with `soksak-plugin-agents-clubhouse.report {turn, text}`, claims the paths it edits with `claim {turn, paths}` and releases them with `release {turn, paths}`. Each command takes only the token of an open turn, which proves the member; a record token is refused with `turn <token> is a record line: only the token of a turn reports, claims or releases`. Each is a record line of the member: `(report) <text>`, `(claim) <paths>` or `(release) <paths>`. Two claims overlap when the paths are equal or one is the other followed by `/`; the room decides each claim in its handler, which runs to its end before another handler, so a claim that overlaps a claim of another member is refused with `paths <path> are claimed by <member>`, and a release of a path that the member does not hold with `path <path> is not claimed by <member>`. The claims of a turn are released when the turn closes.

The room submits the unsent lines at once to each session whose program is `working`, prefixed with `답하지 말고 하던 작업을 계속해.` and without a token, so the member reads them during its work and gives no answer. An idle session receives them with its next turn line or record line, and a blocked session when an event of core.sessions shows it working again. The room keeps two numbers per session: `sent`, the record length of the lines that core accepted, from which the next line starts, and `delivered`, which rises to `max(count, sent)` only on an answer or an acknowledgement. Each session has one submit queue, so the next line of a session is built from the sent number only after core answered the previous submit.

## Room record

The room record is the conversation of the room: the line of each message of the owner, the answer of each member, and each line of the room, in the order in which the room took them. The room appends the line of the owner when `message.send` accepts it, and each answer when it arrives; in `simul` the room appends the answers of a relay in member order after every turn has ended, also the answers of a relay in which another turn failed.

The room delivers the record to each member session. A line of the record is `[@<speaker>] <text>`, with each line break inside the text replaced by a space, and the lines of one submit are joined with ` | `, because `core.session.submit` refuses CR and LF. For each session the room keeps the delivered number `d`, the number of record lines that the session has received (`delivered` of the [tab state](#restart)); a session without a number has received no line. The record lines that a session has not received are the lines from `d` to the end of the record, without the lines that its member spoke itself, because the member gave them. The delivery keeps these invariants:

- Turn completeness: the line of a turn holds the record lines that the session has not received, in record order, so the member reads every line spoken before its answer.
- Closing completeness: after each relay the room sends each member session the record lines that it has not received ([closing delivery](#closing-delivery)).
- Exactly once and in order: each submit carries the lines from `d` to the length `n` of the record when the room built it, and the token of the submit records `n`. The number `d` rises to `n` only when the [answer](#answer) of a turn token or the acknowledgement of a record token arrives, because an accepted submit does not tell that the program read the line (core `docs/spec/persistent-services.md#owned-sessions`). The number never falls, so the submits of a session cover the record from 0 without a gap and without an overlap.
- One open line per session: a session has at most one open token, of a turn or of a record line. A later line for the session waits until that token is answered or acknowledged and the program of the session reports `idle`, so the next line never lands in a turn of the program.
- Restart recovery: the open tokens are kept in the tab state, so an answer or an acknowledgement that arrives after a restart raises `d` and the room then delivers the lines that are left ([restart](#restart)).

A send in which core accepted no submit of the line of the owner withdraws that line: the room removes it from the record and from the conversation, and `message.send` reports the failure through the error display ([commands](#commands)), which keeps the reason. No session received the line, so no delivered number exceeds the record. The record holds no message that no member received, so a repeated send after such failures leaves one line of the owner. A failed send in which core accepted a submit keeps the line of the owner and the answers that arrived, and the room appends `[@clubhouse] the relay failed: <reason>`, `<reason>` being `member <id>: <reason>` of the failed turn, so every member reads that the relay failed.

## Closing delivery

After each relay, whether it ended normally, by the turn limit, by the stop of the owner, or by a failure, and in every mode, the room first withdraws the line of the owner or appends the failure line ([room record](#room-record)) and then sends the record lines that each member session has not received. The sessions of the closing delivery are the sessions of the checked members that `core.sessions` lists and that received the [room protocol](#room-protocol); a member whose check was cleared receives the lines at the first turn after its next check. A session whose unreceived lines are all lines of its own member receives no submit: its delivered number becomes the length of the record.

The record line is `답은 하지말고 알고있어. [@owner]와 [@<member1>], [@<member2>]의 대화기록이다. 답하지말고 참고해.` followed by ` | `, the record lines that the session has not received, and ` | [@clubhouse] record <token>`, a random token of a new record turn of the session; the names are the members that speak in those lines, in the order of their first line. The member acknowledges it with `soksak-plugin-agents-clubhouse.record.ack {turn}` and answers nothing. The acknowledgement raises the delivered number to the length of the record when the line was built; a token is acknowledged once, and a token of no open record line is refused with `turn <token> is not an open record line of this room`; the answer command refuses a record token with `turn <token> is a record line: acknowledge it with soksak-plugin-agents-clubhouse.record.ack`, and the acknowledgement refuses a turn token with `turn <token> is a turn: answer it with soksak-plugin-agents-clubhouse.answer`. While the room waits for the acknowledgement, the member is in `waiting` of the [conversation status](#conversation-status) with the step `record`. The wait ends only with the acknowledgement of its token, because the current program state proves no reading.

`message.send` resolves when the closing delivery has submitted its lines; the waits for the acknowledgements continue after the relay. A later `message.send` is accepted during these waits, and the turn line of a member whose record line is open is submitted after its acknowledgement and the next `idle` of its program. `conversation.stop` also ends each wait for a record acknowledgement: the room closes the token, reports `error: room record: member <id>: record wait stopped`, keeps the delivered number, and sends that session no closing delivery until the next relay, so its next turn or closing delivery carries the lines.

A session that is not `idle` at the closing delivery, such as a failed or a `blocked` member, receives no line: the room reports `error: room record: member <id> is <state>` (`<state>` is `without a program state` when the session reports none), keeps the delivered number, and marks the session as pending in `delivery` of the [conversation status](#conversation-status). A refused submit is reported as `error: room record: member <id>: <reason>` and marks the session pending as well. While no relay runs, each value of `core.sessions` in which a pending session is `idle`, each answer or acknowledgement of a token, and the end of the start of the room run the closing delivery again for the sessions that have lines to receive. The room reports the state of a pending session once when it becomes pending. A session that ends leaves the delivery; a session that a later summon opens for a member has no number and receives the whole record at its first line.

When no relay runs and no wait of the closing delivery is open, every session of the closing delivery that is not pending and whose record wait was not stopped has `delivered` equal to `length` in `delivery`.

## Conversation status

The declared status `soksak-plugin-agents-clubhouse.conversation` carries the conversation that the page shows: `{entries: [{speaker, text}], waiting: [{member, session, step, program}], delivery: [{member, session, delivered, length, pending}]}`. `entries` are the entries of the [room record](#room-record) in record order, `speaker` being `owner`, the identifier of a member, or `clubhouse` for a line of the room ([conversation](#conversation)). The room publishes a new value at each change of the record, also when a failed send withdraws the line of the owner, so a caller reads the conversation from the status and not from the drawn page.

`waiting` names each member whose turn the room waits for, in the order in which the waits began: `step` is `protocol` from the start of its [room protocol](#room-protocol) turn, which waits for the first `idle` of the session, until that turn ends, `answer` from the submit of a relayed line until its [answer](#answer) arrives or the turn fails, and `record` from the submit of a record line of the [closing delivery](#closing-delivery) until its acknowledgement arrives or `conversation.stop` ends the wait. `program` is the program state of the session in the current value of `core.sessions`: `idle`, `working` or `blocked`, `null` while core reports none, and `ended` when `core.sessions` no longer lists the session. A program that stops at a question of its own before its first `idle`, such as the folder-trust prompt of Claude Code at the first start in a folder, keeps its member in `waiting` with the step `protocol`: the room answers no question of a program, because the answer is a decision of the person, so the room shows which member it waits for, and the person answers in the tab of that member. `delivery` names each session of the [closing delivery](#closing-delivery) in roster order: `delivered` is its delivered number, `length` the length of the record, and `pending` whether the room waits for the next `idle` of the session to deliver its lines; a session whose `delivered` is below `length` outside a relay and outside a wait has a line that it has not received. The room publishes a new value when a wait begins or ends, at each change of the record or of a delivered number, and at each value of `core.sessions`, with no timer. Below the conversation the page shows one line per waiting member in the language of the page: `waiting for <name>: <step>, program <program>`, in Korean `<name> 기다리는 중: <step>, program <program>`, `<name>` being the roster name.

## Conversation view

The room view draws each record entry as a speech bubble. A bubble of the owner sits on the right, a bubble of a member on the left; the name of the speaker and its role go above the bubble. Each member has its own bubble color, the color of its place in the roster modulo six, so the color stays the same while the roster keeps its order; the owner bubble takes the accent token of the core theme, and the member colors mix the card token of the theme with a hue. A line of the room (`clubhouse`) is a centered system line. A report, a claim or a release of a member ([work reports](#work-reports)) is a compact note under the answer bubble of the turn in which the member gave it, or under its last bubble when no answer follows. The sections of an answer ([sections](#sections)) are separate blocks inside its bubble, each headed by its addressee. A divider with the round number goes before the first answer after a line of the owner and before each answer of a member that already answered since that line, so each round of the [settling](#settling) is visibly separated.

## Follow mode

The conversation view follows new entries only while it is at the bottom, which is when the last entry is fully visible within 4 points. While it follows, each draw with new entries scrolls to the last entry. When the person scrolls up, the view is in reading mode: a draw keeps the scroll position, and the new entries are added below it. In reading mode a pill at the bottom of the card shows the number of entries below the viewport that have not been visible since the person scrolled up, as `새 대화 3개 ↓`; an IntersectionObserver of the view reports each entry that becomes fully visible, so the number falls as those entries scroll into view, and the room uses no timer. Reaching the bottom by scrolling clears the number, hides the pill and follows again. The pill is the declared element `pill`, which runs the declared command `conversation.scroll.bottom`: it scrolls to the last entry and follows again. The declared status `soksak-plugin-agents-clubhouse.view` carries `{following, unseen}`.

## Timing

Each record entry keeps `at`, the time at which the room took it in epoch milliseconds, and an answer of a member keeps `elapsedMs`, the milliseconds from the accepted submit of its turn line to the arrival of its answer; every other entry has `elapsedMs: null`. The entries of the tab state and of the [conversation status](#conversation-status) carry both fields, and the reader of the tab state refuses an entry without them with `room tab state: conversation must be an array of {speaker, text, at, elapsedMs}`. An entry that the room took before it recorded times has `at: null` and `elapsedMs: null`, and the view shows it without a time. The bubble of an answer shows its time as seconds with one decimal, such as `12.4초`. A waiting member ([conversation status](#conversation-status)) shows the time since the room began to wait for it; the view advances that counter on the display frames of the window through `requestAnimationFrame`, so it follows the refresh rate of the display that shows the window, and stops when no member is waited for.

## Answer

A member delivers its answer through the declared command `soksak-plugin-agents-clubhouse.answer {turn, text}`, not through its screen. A program that draws on the alternate screen, such as Claude Code, writes only the rows of its visible viewport to the terminal, and a row that leaves the viewport is never written; so neither the screen nor the retained rows that `core.session.read` reads hold an answer taller than the member tab, nor the submitted line once it has left the viewport, and the room reads no answer from them.

- For each relayed line the room opens a turn with a new random token and ends the line with ` | [@clubhouse] turn <token>`. A session has at most one open turn.
- The answer command accepts `text`, a string that is not empty after trimming, for the open turn of `turn`, and the answer is `text` unchanged. It ends that turn: a token is accepted once, and a token of no open turn, also a token whose turn has ended, is refused with `turn <token> is not an open turn of this room`. An invalid parameter is refused with `turn must be a non-empty string, got <value>` or `text must be a non-empty string, got <value>`.
- The turn of the member ends when its answer arrives. The member runs the command during its turn, and core answers a command after the handler of the room ran, so the answer arrives before the program reports `idle`. A turn whose program goes `working` and then `idle` without an answer fails with `the member ended its turn without an answer: it ran no soksak-plugin-agents-clubhouse.answer`. A turn whose program reports `blocked` fails as before ([modes](#modes)), because the room answers no question of a program; a member whose program asks permission for the answer command needs that permission from the person.

A failed turn fails with `member <id>: <reason>` ([modes](#modes)).

### Decision

The answer comes through a declared room command whose call carries the token of the turn. The reasons and the objections that an adversarial review raised against the decision:

- The screen and the retained rows cannot hold the answer: the recorded output of Claude Code holds only the rows of its visible viewport, so the earlier rule, which took the reply block from the rows after the submitted line, failed for every answer taller than the tab.
- Identity of the member. Core gives the handler of a command no caller, and `agent.surface` answers the owner surface for every process of an owned session (core `docs/spec/persistent-services.md#owned-sessions`), so no identity of core tells the members of one room apart; such an identity needs a change of the terminal sidecar and of every host. Objection: a session parameter is no proof, because `core.sessions` lists every session and in `simul` every member has an open turn, so one member could answer for another. Answer: the token is random, new for each relayed line, and written only into the line of its member, so an answer with the token comes from the terminal that received the line, and the room needs no identity of core.
- Objection: a second or a late answer could end a later turn of the same member. Answer: each token is accepted once and only while its turn is open.
- Objection: the program could report `idle` before the member answers. Answer: a program that waits for a permission reports `blocked`, which fails the turn with its own reason, and `idle` means that the program ended its turn; the line asks the member to deliver the answer as the last step of the turn.
- Objection: the sessions that received the earlier protocol line know no answer command. Answer: the tab state names the sessions of the current protocol `protocolSessions` and refuses the earlier field `taught`, so those sessions receive the protocol line again ([restart](#restart)).
- Objection: a long answer of several lines is hard to quote in a shell. Answer: the protocol line names the MCP tool `command_run` first, whose parameters are JSON, and gives the shell form with a quoted here-document.
- Rejected alternative: `sok message send` writes a message into the folder of a terminal, and the room is no terminal folder.
- Rejected alternative: `sok conversation read` reads the conversation file of an agent, but it selects the file by the working directory and not by the session, so members in one folder cannot be told apart, and it is a read without an event of the end of the answer.

## Restart

A restart of the application, an unload of the room tab and a restart of its view show the room as it was, without input. The room declares `surface.unload` `{format: 1, maxBytes: 1048576}` and writes the state of its tab through the tab state of its view (`tab.state.write`) at each change; core keeps it per tab across a restart (core `docs/spec/plugins.md#memory-saver`). The state is `{roster, mode, conversation, sessions, protocolSessions, delivered, turns}`:

- `roster`: the entries `{id, checked}` in roster order. At start the first roster that the definitions give keeps this order and these checks; a definition that is not in it joins unchecked at the end, and an entry without a definition leaves.
- `mode`: the conversation mode; the setting `kibitzDefault` gives the mode only of a room tab without a state.
- `conversation`: the entries `{speaker, text}` that the conversation shows, `speaker` being `owner` or the identifier of a member and `text` the message or the [answer](#answer) of the member, so the conversation shows the same answers after a restart.
- `sessions`: the member sessions that this room opened.
- `protocolSessions`: the sessions that received the [room protocol](#room-protocol) with the answer command; a session in it receives no protocol line again.
- `delivered`: an object that maps a member session to the number of [room record](#room-record) lines that the room delivered to it, an integer from 0 to the length of `conversation`.
- `turns`: the open tokens `{turn, session, member, kind, count}`, `kind` being `answer` for the token of a turn and `record` for the token of a record line, `member` the identifier of its member and `count` the length of the record when the line was built, an integer from 0 to the length of `conversation`. After a restart the room accepts their answers and acknowledgements: either raises the delivered number of the session to `count`, and an answer of a turn whose relay ended with the restart is appended to the record as the answer of `member`. A wait of a token kept from before the restart ends only with its answer, its acknowledgement or `conversation.stop`.

The reader accepts only this form and refuses any other value with `room tab state: <field> ...` naming the field and what it found, and a field outside this form, such as the earlier `taught`, with `room tab state: unknown field <field>`; a tab without a state reads `null`. A state whose JSON is larger than the 1048576 bytes of `surface.unload` is not written and is reported as `error: room tab state: the state is <n> bytes, over the limit of 1048576 bytes`; a refused write is reported as `error: room tab state: <reason>`.

At start the room waits for the first value of `core.sessions` and summons the checked members of its state. It reattaches only to the sessions that `core.sessions` lists with this room surface as `owner`: a member whose stored session is one of them keeps it, and only a member without one opens a session. The arrangement applies the same tree, so core resolves each entry `{plugin, params: {session, title}}` to the member tab that shows that session already. A tab of the plane whose `params.session` names a session of `sessions` that `core.sessions` no longer lists is a member tab of this room whose session ended; the room closes it with `core.layout.close {tab}` after the apply, and then keeps in `sessions` only the open sessions. The room closes no other tab.

A room tab without a state has no saved roster: it waits for the first value of `core.sessions` and checks each member whose stored session (project data `room_member_sessions`, the document `<room surface>/<agentId>`) `core.sessions` lists with this room surface as `owner`, then summons them, so it reattaches to its own sessions; every other member stays unchecked, the mode is the setting `kibitzDefault` and the conversation is empty, because no record holds them. The document of a member relation is `{surface, agentId, sessionId, cwd, savedAt}` with the identifier `<room surface>/<agentId>`, so two rooms of one project keep separate relations; the store refuses a document of another form with `room_member_sessions <id>: <field> ...`. A summon counts each session that it opened as open until `core.sessions` lists it, so a summon that runs before `core.sessions` lists a session opens no second one; a session whose relation the store refuses to put is ended with `core.session.end {session}`, and the summon rejects with the reason. A session that opens takes the measured size of the room card in points and the backing scale of the window. A card that is not laid out yet, or a hidden room, measures zero, and the room waits for the first resize event of its view with a positive width and height, so it sends `core.session.open` with no size that core refuses; a reattach measures no size.

While a message is relayed the room reports `tab.keep {reason: "busy", on: true}`, so core does not unload the page that waits for the turns.
